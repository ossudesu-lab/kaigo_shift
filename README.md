# kaigo_shift

ショートステイ施設のひと月分の勤務表を、制約最適化（CP-SAT / OR-Tools）で作る。

職員は17名。このうち**変則勤務プールの10名**は早出・遅出・夜勤・当日リーダーを
担うため、組み合わせをソルバーで解く。残る7名は日勤と休みしかなく、
プール側と枠を奪い合わないので別に解く（19分かかる求解に上乗せせず、数秒で終わる）。

> ステータス: 2026年7月〜11月の5か月分を、現場の実績シフトと突き合わせて検証中。

## 何が難しいか

勤務表は「1人1日1勤務」を割り当てるだけの問題に見えて、実際には勤務どうしが
時間的に連鎖する。夜勤入りの翌日は必ず明け、明けの翌日は必ず休み。月末の夜勤入りは
翌月へ繰り越す。遅出の翌日に早出は入れられない。この連鎖があるため、
1日ずつ埋めていく素朴な方法では破綻する。

さらに「守らなければならない条件」と「できれば避けたい条件」が混ざっている。
前者をハード制約、後者をペナルティ付きのソフト制約として分け、
**実績シフトに寄るように重みを調整する**という形で解いている。

## 制約

ハード制約は15。設計書の4章に1〜15で列挙してある。おおまかには

- 勤務の連鎖（入 → 明 → 休、月をまたぐ繰り越し）
- 職員ごとに担当できる勤務種別、リーダー可否
- 月間の休日数・夜勤回数・連続勤務日数の上限
- 固定休の曜日、確定済みの希望休、有給

ソフト制約はペナルティの重みで表す。「連続勤務が5日」「日遅（1人で2枠を兼ねる）の
使用」などに点数を置き、目的値を最小化する。重みは思いつきではなく、
**実績シフトを再現できるかどうかで決めた**。

## 設計

`shift_solver_design.md` に、制約の導出から重みの決め方まで書いてある。
実装より先に、現場のルールを制約の形に翻訳する作業をここでやっている。

`RUNBOOK.md` は月次の運用手順。

## データについて

**このリポジトリに実データは含まれていない。**

元になるのは実在する施設の職員17名の勤務条件と実績で、Excel帳票には氏名が入る。
いずれも `.gitignore` で除外し、さらに `scripts/pre-commit` でコミット自体を
止めている。非公開リポジトリであっても、一度履歴に入れれば公開に切り替えた瞬間に
露出するため、最初から入れない方針を取っている。

番人の導入:

```
cp scripts/pre-commit .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

動かすには `data/` に自分のデータを置く必要がある。必要な列と形式は
`shift_solver_design.md` の3章にある。

なお設計書・コード中では**職員を実名で書かない**。`S01` 形式の匿名IDのみを使い、
実名との対応は手元のExcelの並び順だけが持つ。個人の事情（休職の理由など）も
記述しない。IDだけでも職場の人間が読めば特定できるため。
